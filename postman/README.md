# Postman collection

`desk-ticket.postman_collection.json` sends a request to every route built so far, milestones 0 to 4, and checks each response.

It is generated by `build.py`, which takes the knowledge documents from `examples/chunking/`. After changing a route, edit `build.py` and run:

```bash
python postman/build.py
```

## Run it

1. Start the stack:

   ```bash
   sudo docker compose up -d db redis ollama ollama-pull
   make migrate
   make dev       # terminal 1
   make worker    # terminal 2
   ```

2. In Postman, choose **Import** and select `desk-ticket.postman_collection.json`.
3. Open the collection and click **Run**. Untick folder 7, then run. All variables live in the collection itself (Variables tab), so no environment is needed. If the API is not at `http://localhost:8000`, change `base_url` there.
4. Open **View > Show Postman Console** to see a table of hits for each search.

## Folders

| Folder | What it covers |
|---|---|
| 0. Health | `/health`, `/ready`. Also sets a new `run_id`, so every run creates fresh users and workspaces |
| 1. Users and auth | Signs up and logs in owner, agent, member and outsider (tokens are saved). Covers 409, 401 and 422 |
| 2. Workspaces and members | The Acme workspace, roles, and the outsider's own workspace. Covers 403 and 404 |
| 3. Tickets | Create, filter, assign, reply, internal note, a rejected system message, resolve, and events |
| 4. Knowledge and ingestion | Documents, a ticket answer, approve, reject and edit, then waits for the worker. Checks that every chunk has a vector |
| 5. Search | Keyword, vector and hybrid, with the expected top results |
| 6. Search rules | Tenant isolation, roles, validation, and archive hiding a source at once |
| 7. Manual: Ollama down | Run `sudo docker compose stop ollama` first. Hybrid returns `degraded: true` and vector returns 503 |

## Reading failures

- **Worker checks fail** ("Wait for … ingestion"). Is `make worker` running, and can it reach Ollama? The test message shows the job's `last_error`.
- **Any "mentions …" test fails.** It checks search *quality*, not correctness. Real embeddings decide the order, so read the console table before changing code. Milestone 5 measures these properly.
- **429 on sign-up or log-in.** Those are limited to 10 a minute per IP. Wait a minute before running the collection again.

# Demo collection (seeded data)

`kettle-demo.postman_collection.json` logs in as the people `make seed` creates (see `app/seed/`) and works with their data, instead of building its own. It is generated by `build_demo.py`.

1. Run `make seed-reset`. It loads fresh demo data, and the worker and Ollama must be running.
2. Import `kettle-demo.postman_collection.json` into Postman.
3. Send folder **0. Log in** first. It saves the tokens and both workspace ids.
4. Use the other folders in any order, except that folder 4 needs the ticket folder 3 creates. Folders 2–4 change data, so run `make seed-reset` before running them a second time.

| Folder | What you do |
|---|---|
| 0. Log in | Log in as Maya (owner), Omar (admin), Priya (agent), Sam (member) and Rosa (the other company), then find both workspaces |
| 1. Search playground | Ten real searches. Edit any query and Send; the console shows the result table |
| 2. Review queue | Approve the agent's draft and the pending answer, then watch them appear in search |
| 3. Tickets | Filter the 22 tickets, read one conversation and its history, then take Sam's new ticket all the way to resolved |
| 4. Ticket → knowledge | Turn that resolved ticket into an answer, approve it, and find it in search |
| 5. Tenant isolation | Rosa and Maya can't see each other's data, and Sam, a member, can't use knowledge search |
